# Humanizer — 公共分类法即技能规格（Encyclopedia-as-Skill-Spec）

## 技术定义 (What)
Humanizer 是一个 Agent Skill，唯一职责是消除 AI 生成文本的"AI 味"。它的方法论来源不是自研模型也不是风格微调，而是维基百科编辑用来识别 AI 文本的公开条目 "Signs of AI writing"——把该条目里的特征清单转成 26 条可编号、可排序、可逐条命中的模式（从最强/最常见的 1 号排序到最弱的 26 号），再让 Agent 按"标记 → 重写 → 对模式与原始断言双重校验 → 出终稿"的流程执行。其规格设计的两个关键决定：(1) 明确宣布**不为通过 AI 检测器**服务，检测器仍会标记其输出——把目标从"欺骗判别器"收敛为"服务人类读者"；(2) 前 5 条模式一见即改，标注 "weak alone" 的模式仅在多个同时出现时才动手，避免误伤刻意使用单一手法的成熟作者。安装面覆盖 Claude Code 插件市场、Codex、pi、以及 Skills CLI 可及的所有 Agent。

## 行业痛点 (Why)
AI 写出的文本有一套稳定可识别的"默认选择"痕迹（不是 X 而是 Y、一行式收尾、听起来很深的套话、"问题是"式铺垫、对着无人辩论），这类文本让人一眼看出是机器写的，损害可信度。而"让文本更像人"这件事长期被两种坏方案占据：要么靠模型微调（成本高、不可解释、无法在任意 harness 复用），要么靠"绕过 AI 检测器"（目标本身就错，且注定军备竞赛）。缺少的是一份**可审计、可引用、与模型无关**的规则来源。

## 旧范式 vs 新范式
- **旧做法**：去 AI 味靠两件事：一是换模型或微调一个"更自然"的模型；二是安装"反检测"工具，目标是把 AI 检测分数压下去。前者把风格问题锁死在权重里，后者把目标错设为欺骗判别器。两者都不可审计——你说不清到底改了哪些特征、为什么改。
- **新做法**：把一份**公开的、有编辑实践背书的分类法**（维基百科 "Signs of AI writing"）直接编译成 Agent 可执行的技能规格：每条特征编号、排序、给出改前/改后样例，Agent 逐条命中并展示"初稿 → 自我批评 → 终稿"三段过程。风格治理从"改权重"变成"改规格"，从而获得三个性质：可审计（命中哪几条一目了然）、可移植（同一份 SKILL.md 在 Claude Code / Codex / pi / Gemini CLI / Copilot / Windsurf 通用）、可修正（社群提 issue 改模式表即可，无需重训）。同时显式放弃"骗过检测器"这个错误目标。

## 生产力影响 (How)
对任何需要对外输出文字的场景（发布日志、文档、销售邮件、公告），把"读起来像人写的"从主观品味问题变成**可勾选的检查清单**：26 条里前 5 条一见即改，弱模式仅在共现时处理，减少过度改写。文件模式下只改散文、保留代码/数据/frontmatter/链接目标，适合直接进 CI 或 pre-commit。支持"声音匹配"——贴 2-3 段自己的文字，重写会跟随其节奏、用词、标点与刻意的怪癖。作者给出的盲测结果：评审 16/16 次偏好重写版本（issue #229，自证性质，需独立复核）。

## 采用成本
极低。一条命令安装（`npx skills add blader/humanizer --global --agent '*'` 覆盖全 harness；Claude Code 走插件市场，需 ≥2.1.142）。无 API key、无网络依赖、无额外模型。学习成本约等于读一遍 26 条模式表。风险成本主要是"过度改写"——需要靠 weak-alone 规则与"保留全部原始断言"来约束。
