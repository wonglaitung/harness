# Dharma Field Extractor — Schema-as-Output-Contract 与「宁可 null 不可编造」

## 技术定义 (What)

一个 **2B 参数专用模型**，输入「文档图像 + 输出模式（schema）」，直接输出类型化 JSON。

两条路径：

- **Open（开放）**：不给 schema。模型从版面与上下文中自行识别结构化区域——「标签后跟值」的键值对、带表头的表格——返回所有发现的 key-value 对。适合「不知道文档里有什么」的场景。
- **Schema-directed（模式导向）**：逐字段指定名称与类型（`string` / `number` / `boolean`），输出**严格遵循**该 schema，键名与你的下游系统一致、无多余字段。要求表格则逐行逐列填充；要求嵌套则按文档嵌套输出。

关键行为契约：**schema 要求的字段在文档中不存在时返回 null，不编造值。**

同一个 checkpoint 处理所有文档类型（合同、法院文书、发票、身份证件、表单、医疗申请单），**无按类型微调**。

## 行业痛点 (Why)

OCR 给的是「整页文字」，业务系统要的是「几个字段」。两者之间隔着一层最脆弱的胶水：

拿到发票的逐行 OCR 结果后，没人知道
- 哪个字符串是税率
- 哪个数字是总额
- 哪一行属于哪个明细项

必须写规则或正则把值塞进数据库列。**版式一变，规则就崩。**

通用 LLM 能做这件事，但在高价值、高并发的固定任务上（每天几千张供应商发票、医疗申请单、合规合同），前沿 API 的价格与延迟让「用通用大脑做正则表达式的活」成为明显不经济的方案。

## 旧范式 vs 新范式

**旧做法**
- OCR 出全文 → 写解析规则/正则映射到字段 → 文档版式一变，规则崩
- 或：通用 LLM + 精心设计的 prompt，成本高、延迟高、输出结构靠「希望它遵守」
- 模型倾向于为缺失字段填一个看起来合理的值（幻觉静默污染数据）

**新做法**
- 输出模式前置为输入契约：调用方直接提交目标 schema（字段名 + 类型）
- 模型返回严格符合该 schema 的 JSON，键名与下游系统一致，可直接进下一个系统
- 缺字段返回 `null` —— 幻觉从「静默数据污染」变成「显式缺失信号」

**这层差别是范式级的：前者约束形状（format），后者约束真实性（truthfulness）。**

## 生产力影响 (How)

1. **消除胶水代码**：OCR → 数据库之间的映射层不再需要手写。schema 即接口，下游不改代码适配模型输出。

2. **幻觉可运营化**：`null` 成为一等公民。下游可以用「出现 null」触发人工复核，而不是把编造的金额写进账本。这让「AI 自动化高风险单据流程」第一次有了可审计的失败模式。

3. **经济性转折**：2B 参数在固定高并发任务上以远低于前沿 API 的成本运行，「每张单据都过模型」在成本上成立——这正是专用化论文（arXiv 2604.14314）的核心主张的延续。

## 采用成本

- **接入**：低。portal/API 方式，无需自建推理。
- **一次性定义**：按业务字段写 schema（三种标量类型 + 嵌套 + 表格）。
- **迁移成本**：把既有正则/映射规则翻译成 schema 定义。这是真正的成本所在——但它是**一次性**的，且翻译后比正则更抗版式变化。
- **边界**：schema 表达能力限于 `string` / `number` / `boolean` + 嵌套/列表，无日期、货币、枚举等语义类型（可能需上层校验）。

## 采用案例

- **供应商发票批次**：每早一批发票，取 supplier / invoice_number / due_date / total 四个字段入库；明细项返回为有序列表，每项自带 quantity 与 value
- **医疗申请单 → 排程系统**：取患者姓名、检查类型、日期，直接进调度
- **合规合同**：取当事方、期限、罚则、罚款金额，喂入合规系统
- **身份证件 → 员工档案**：字段映射到员工记录已有列名

## 风险/局限

- **「不做长尾」的代价**：2B 专用模型在任务分布外的文档类型上可能显著弱于前沿模型，需要划定适用范围
- **类型系统过窄**：只有三种标量类型，缺日期/货币/枚举/正则约束，语义校验需在其上另建一层
- **商业闭源**：模型权重未公开（仅 OCR-LITE 开源），采用即接受供应商锁定
- **null 语义的双面性**：`null` 同时代表「文档没有这个字段」与「模型没找到」，二者在下游可能需区分
- **前置声明成本**：schema-directed 的前提是「你已经知道要什么」，探索性场景仍需 Open 模式 + 后处理

## 与 VocabX 的同一转向

同一周内出现两个结构相似的信号，值得并列观察：

- **VocabX**（2026-10-21）：按 token *价格* 而非频次重建词表 → **成本是目标函数，不是事后账单**
- **Dharma Field Extractor**（2026-11-04）：按 schema *契约* 而非格式提示产出字段 → **真实性是约束，不是提示词里的请求**

两者都是同一种成熟化动作：把原本靠「通用大模型 + 愿望式 prompt + 事后校验」的模糊地带，重写成一个**显式的、可机器校验的目标**。这可能是 2026 下半年最值得追踪的一条主线。
