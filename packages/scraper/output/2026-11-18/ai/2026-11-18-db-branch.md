## 技术定义 (What)

用 ZFS clone 实现 MySQL / PostgreSQL 的秒级写时复制分支。base 是装好真实数据的 ZFS dataset；branch 是 base 快照的 clone，创建时 **0 字节拷贝**，每个分支跑独立数据库实例、占独立端口。可选 ProxySQL 按用户名或 `/*db_branch='name'*/` 查询注释把连接路由到对应分支。多节点组成 Raft 集群共享 base / branch / 配置 / 用户。

## 行业痛点 (Why)

Agent 需要**真实数据**才能验证行为，但让它连生产库是最危险的一步。此前只有两条坏路：
- 接只读副本 → 数据是旧的，且不能写，迁移类任务无法测；
- 手工 dump/restore → 几十 GB 的库要几十分钟，"每个 PR 一份数据库"根本不可行。

结果：Agent 要么在假数据上"测过了"，要么带着写权限碰生产。

## 旧范式 vs 新范式

- **旧做法**：dump/restore 或全公司共用一套 staging。慢、脏、状态互相污染，CI 里一份库排队用。Agent 沙箱只隔离文件系统，**不隔离数据层**。
- **新做法**：分支是原语，沙箱是组合。Agent 通过内置 MCP server 自己 `branch create` → 跑危险查询/迁移 → `branch delete`，生产库永不被触碰。每个 PR / CI run 分配一份秒级就绪的独立库，`--ttl` 到期自毁。

## 生产力影响 (How)

- **Agent 安全从权限问题变成拓扑问题**：给它一份可随手毁掉的分支，就不必在"能力"和"安全"间取舍。
- **migration / 版本升级可预演**：`branch upgrade --check-only` 先看 MySQL 8.0→8.4 会撞到什么；真升级前自动存 checkpoint，失败自动回滚，且只动这一个分支。
- **PR 级数据库隔离成为默认**，而不是大公司的特权。
- **checkpoint / restore**：`branch reset` 回创建态，`branch checkpoint` 瞬间存点，`branch restore` 回滚且历史 checkpoint 全部保留可回。

## 采用成本

- 需 Ubuntu 24.04 / 26.04 + 一个 ZFS pool（`zfsutils-linux` 作为依赖装上）。
- 安装：apt 源四行命令 + `db-branch init --pool <zpool>`；本地试用一条 Multipass 命令起 VM（约 2 分钟）。
- **自托管、无云版**。核心 Apache-2.0 免费；auth/SSO、audit、history、diff、FSx 存储为闭源付费模块（license key，月/年）。
- 学习曲线在 ZFS 与 base/branch 心智模型，不在 CLI（CLI 很直白：`branch create / reset / checkpoint / restore / delete`）。
- 性能：官方 3 节点集群实测 PostgreSQL 分支约 **0.5s**、MySQL 约 **3s**。

## 采用案例

- **AI agent sandbox**：README 列为第一用例——Agent 在分支上跑有风险的查询或迁移，然后删掉分支。
- **每 PR 一份数据库**：每次 CI run / PR 分到一份大库的副本，秒级就绪，`--ttl` 自动清理。
- **版本升级检查**：在单个分支上跑大版本升级，`--check-only` 预演。

## 风险/局限

- **Beta**：作者明确说 1.0 前 API 与 CLI 细节可能变，不适合当稳定基础设施押注。
- **强绑定 Linux + ZFS**：macOS / Windows 用户只能开 VM 试用；ZFS 运维本身有门槛（内存、ARC 调优）。
- **付费模块闭源**：企业真正需要的审计、SSO、diff 都在付费墙后；"开源自托管"的完整性有限。
- **社区验证极弱**：HN 45 分、无第三方引用，属于"概念先行、生态未起"。
