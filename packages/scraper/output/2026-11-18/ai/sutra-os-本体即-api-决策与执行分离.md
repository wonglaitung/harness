## 技术定义 (What)

一个开源自托管的本体（ontology）平台，把组织的全部数据收敛成「一个你自己拥有的模型」。

三个原语撑起全部设计：
- **object types** —— 有什么（比如：一批干草，来自某块田、某次收割）
- **link types** —— 关联谁（比如：一笔销售，卖给某个买家）
- **action types** —— 能做什么

两条关键约束定义了这个范式：

1. **单一写入口**：所有写入必须经过一个 action，服务器会拒绝非法写入**并给出理由**。
2. **决策与执行分离**：每一次变更都是 proposal，直到被批准才落库。人类与 AI Agent 都只能 propose —— 「deciding is not doing」。

模型本身被生成为类型化的 API：Python SDK、CLI、REST API、git、AI Agent 全部走同一套服务器强制的规则。每个数字都能通过 Data Lineage 追溯回源头。模型和数据都可以在分支上（branch）修改。

## 行业痛点 (Why)

核心痛点：**没人知道什么依赖什么**，因此级联失效无法事前推演。

作者列出的四次真实事故构成论证：
- 2017 **NotPetya**：通过一个乌克兰会计软件传播，连带停掉马士基的港口和默克的工厂
- 2023 **FAA**：一个损坏文件导致全美所有国内航班停飞
- 2024 **CrowdStrike**：一个错误更新让数百万 Windows 机器崩溃，航空公司、医院、银行静止
- 2026-11：一个厂商把 Outlook 弄下线一天，部分城市退回传真；同周 FAA 电信网络被数据淹没、老化路由器崩溃，出现美国史上第三次全国性停飞 —— **「没人把这些路由器放在那张维系飞行的图上，所以事前没人能问：它们挂了会停什么」**

这正是 Sutra-OS 要回答的问题：每个系统、设备、数据集、决策都成为带上下游链接的对象，于是持有这个模型的人可以在故障发生**之前**问「某一部分失效会停什么」，并得到答案——从单一个人到政府，各个尺度都成立。

## 旧范式 vs 新范式

- **旧做法**：数据散落各家 SaaS 与内部系统，schema 藏在应用里；写操作可以来自任意方向（脚本、ORM、后台任务、Agent），没有单一关卡；Agent 拿到写权限就直接执行，审计靠事后日志回放；指标口径与血缘靠文档和口头约定。
- **新做法**：本体先行——先定义「存在什么、怎么连、能做什么」，模型即 API 的唯一真相源。所有写入必须经过声明的 action，服务器强制执行。变更默认是 proposal 而非 fact，人类批准后才落库，因此每次修改都有人负责。数字沿 lineage 回溯到源，权限由服务器通过 markings 强制而非应用层自愿遵守。

## 生产力影响 (How)

对 Agent 时代最关键的一点：**给 Agent 一个结构性无法越权的写入面**。

Agent 不需要被信任——它只能提交 proposal，服务器按声明的 action 规则裁决。这比「在提示词里请求 Agent 不要删数据」强一个数量级，也比事后审计日志强，因为非法写入从设计上就无法发生。

对组织而言，获得「事前可问」的能力：不用等宕机复盘，而是提前查询某部分失效的传播路径。

代价：写入有延迟（proposal → 审批 → 落库），且需要真正的建模工作——建本体比建表慢得多，这是很多团队会卡住的地方。

## 采用成本

- **技术栈门槛**：Linux x86_64 + JDK 21 + Clojure CLI + Node.js + Python 3 + git。后端是 Clojure —— 强大但小众，直接限制了贡献者池，这是单人项目状态的根因之一。
- **建模成本**：需要实质性本体建模，不能即插即用。
- **Beta 风险**：模型语言与 API 在版本间仍可能变化，UI 与文档部分未完成。
- **运维自负**：自托管，含内嵌 PostgreSQL，数据在 `$SUTRA_HOME`。
- **可持续性**：单人项目，README 首页明确「Maintainers wanted」。AGPL-3.0-or-later 保证 fork 权，但也意味着没有商业实体背书。

快速验证路径：`git clone && bin/sutra-solo` 起内嵌 PostgreSQL + 服务器，示例模型在 `resources/presets`（一个农场的完整模型）。

## 采用案例

- **农场预设模型**（`resources/presets`）：干草批次 ← 田块 ← 收割，销售 → 买家，含 Data Lineage 从源经数据集、转换到 object types / links / actions 的完整链路。可作为本体建模的参考实现阅读。
- **文档协同编辑**：Writer、Calc、Visio 类文档可在模型上实时协同编辑 —— 这是少见的「本体平台带完整前端」组合。
- 尚无第三方生产采用案例可引用。

## 风险/局限

- **单人维护 = 最大风险**。概念再强，缺乏维护者意味着安全响应、版本兼容、长期演进都无保障。评估时应按「学习用参考实现」而非「生产依赖」来对待。
- **Clojure 技术栈**缩小了贡献者池，恶性循环。
- **Beta 的不稳定契约**：模型语言会变，意味着现在建的模型未来需要迁移。
- **写入延迟 vs 敏捷性**：proposal 审批流程适合高价值、低频率的变更（财务、库存、审批），不适合高频写入场景（日志、遥测）。
- **没有明确的安全审计**：作为面向「不可信 Agent」的执行层，其自身的安全模型是否经受过对抗测试尚未披露。
- **定位含政治宣言**：README 有相当篇幅的反平台垄断论述。概念价值真实，但需自行剥离叙事与工程现实。
