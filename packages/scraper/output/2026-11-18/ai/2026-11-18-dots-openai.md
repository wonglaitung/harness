# dots (OpenAI) — 常驻 Agent 拥有独立云电脑 + Agent 身份成为组织一级主体

## 技术定义 (What)

dots 是 OpenAI 的"常驻型 Agent"产品形态：每个 dot 由 GPT‑6 系列模型驱动，拥有自己的云电脑、自己的浏览器、以及用户已连接的 4,000+ 应用；可通过 ChatGPT（桌面/Web/移动）、Slack、Teams 触达，并可语音通话。它会基于反馈长期学习用户偏好，在用户不主动提问时也会后台运行（官方称之为 proactive research）。安全上，后台工作被限制在只读工具内；涉及账户或信息外发的动作走 auto-review，对照用户指令、Custom Rules 与安全要求决定"可执行 / 需批准 / 必须用户本人做"。

## 行业痛点 (Why)

此前的"个人 Agent"存在一个结构性矛盾：要让 Agent 有用，就得给它真实的执行面和凭证；但一旦给了，它就与用户的设备、会话、权限绑死，既无法后台长跑，也无法被审计与授权。结果是大部分 Agent 停留在"用户在场、逐步指挥"的层面。dots 的做法是把 **执行环境（云电脑）** 与 **用户环境（本机）** 分离，再把 **身份（specialist dot 的独立凭证）** 与 **调用方（用户）** 分离——这样 Agent 才能被当作一个可授权、可审计、可挂起的组织主体来管理。

## 旧范式 vs 新范式

- **旧做法**：Agent 跑在用户电脑上或借用用户会话；用户必须在场逐步指挥；权限等于"用户权限的全集"；后台运行等于"无约束地乱动"。
- **新做法**：Agent 有独立云电脑，用户设备默认隔离（除非显式连接）；后台主动工作时工具被限制为只读；组织内 Agent 有自己的身份与凭证，纳入既有访问治理体系（Agent 365）。

## 生产力影响 (How)

对个人：把"需要连续几小时/跨多应用推进"的工作从"用户在场驱动"变成"给目标 + 偶尔审批"。官方客户案例中，员工把 dot 视为"一切工作的编排者"，每天两小时语音对话，并让 dot 直接操作 After Effects / Rive 完成原本需数天的 3D 动画（约十分钟）。对组织：specialist dots 意味着可以把采购、发票处理、邮件营销、客服、商务合同等**边界清晰、结果可验收**的职能整体交给一个带身份的 Agent，而不是让每个人各自维护一套私人自动化。

## 采用成本

- 成本：随 Pro / Business Premium 套餐附带首个 dot；超出部分按"加速或增加月度工作量"计价。
- 迁移成本：中高——需要重新设计权限边界（Custom Rules）、确定哪些动作必须人工批准、以及为 specialist dot 规划身份与系统对接。
- 学习曲线：低（交互即对话），但治理设计曲线高。

## 采用案例

- **Holiday Extras（英国旅游科技）**：VP of AI 的 dot（名为 Beast）在新功能上线次日主动发现上线事件、经 ChatGPT 插件拉取 BigQuery 数据并交付报告，用户并未提出请求；同一 dot 被授权访问 Slack、收件箱、Drive 与本机，用于早晚简报与 3D 动画制作。
- **OpenAI 内部**：Slack 出现 bug 时 dots 立即开始排查；新设计到位时 dots 直接产出可运行应用；规划周期中维持团队同步。

## 风险/局限

- **后台只读约束是产品承诺，不是能力上限**：一旦用户显式连接本机或授予写权限，隔离假设即失效。
- **auto-review 是判定层，不是保证**：官方明确"dots 仍会犯错，重要工作需复核"；敏感操作（如改密码）始终保留给用户。
- **组织级 Agent 身份带来新的攻击面**：一个持有凭证、能长期自主运行的主体，本身就是需要红队化的对象。
- **可用性受市场与套餐限制**：目前仅 Pro / Business Premium 合格市场，Enterprise 需管理员开启 beta。

## 为什么判定为新范式

1. **概念创新**：把"Agent 的执行环境"和"Agent 的身份"分别从用户侧剥离，形成两个可独立治理的对象——这是形态变化，不是能力升级。
2. **采用广度**：4,000+ 插件生态 + Microsoft Agent 365 企业治理集成 + 多档套餐开放。
3. **时间新鲜**：2026-11 首发，远在 6 个月内。
