# Palette — Design-Language Distillation（自有设计语言的蒸馏）：设计师/编码者角色拆分 + PresentBench 可行性基准

## 技术定义 (What)
用一个 20B 开源权重模型，通过「单一 LoRA 承担两个角色」的方式复现人类做 PPT 的真实流程：designer 角色先输出结构化 JSON brief（配色、字型系统、每页布局、精确内容、以及一条设计理由），coder 角色再拿单页 spec 写出 pptxgenjs 代码。两个关键设计：(1) 把「编辑判断（讲什么）」与「几何计算（放哪里）」强制解耦到两次调用，且 brief 是人类/Agent 可读可改的中间契约；(2) 因为每页 context 在写代码前已固定，coder 调用可完全并行，编码阶段快 6–7 倍。

## 行业痛点 (Why)
前沿模型能做出漂亮的 deck，但做出十个就像十个：同一套「有品味的默认值」、同一种 house style、一股淡淡的「AI 生成味」。你让它套用自己的模板，任何 prompt 都拦不住它漂回自己的风格。而企业 deck 常常涉密，根本出不了内网。这两个约束都指向「一个自己拥有的模型」——开源权重、跑在自己基础设施上、用自己设计语言训练。但现实是：小开源模型在这件事上很糟糕，产出的 deck 标题融进背景、文字跑出页面、形状层层叠压。

## 旧范式 vs 新范式
- **旧做法**：要么用前沿云模型 + prompt 强行约束风格（必然漂移，且涉密内容外流），要么用模板系统/规则引擎（无法处理编辑判断，deck 千篇一律）。小开源模型被判定为不可用——因为没人相信它能一次做对布局几何。
- **新做法**：§合成数据 + 角色拆分 + harness 验证，把「小模型做不好 deck」变成可解决的问题：用大开源教师模型合成约 1000 份 deck / 约 10000 页的「计划 + 设计理由 + 页面代码」数据集（每个样本带反事实推理痕迹），LoRA 微调 20B 模型，再用 harness 检查渲染结果。核心赌注：小模型 + 自有设计语言 + 验证闭环，可以追平前沿系统，同时你保留成果所有权。

## 生产力影响 (How)
在 PresentBench 的三个测量域中两个排名第一，超过前沿基线。工程上两个可复用红利：brief 契约让单页可局部修改而不重生成整份 deck（人机协作的关键接口）；coder 并行化带来编码阶段 6–7× 提速。对企业意味着「设计语言资产化」——品牌规范从一份 PDF 变成一份可以训进模型的训练数据 + 一个可自托管的模型权重。

## 采用成本
中高。需要：自有设计语言的结构化沉淀（配色/字型/布局规则要先能被写成 recipe）、合成数据生成链路（依赖大教师模型）、LoRA 训练算力（20B 级）、以及一个能渲染并判定「文字是否跑出版面」的 harness。调试经验：coder 样本长度约为 designer 的 5 倍，朴素混采会把 designer 训不足，需 5× 过采样。
