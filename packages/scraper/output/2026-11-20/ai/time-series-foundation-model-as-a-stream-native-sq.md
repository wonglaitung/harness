# Time-Series Foundation Model as a Stream-Native SQL Primitive（时序基础模型降为流处理器的内置 SQL 函数）

## 技术定义 (What)
把预训练的时序基础模型（IBMs TTM 家族，累计 5000 万+ 下载）编译成 Apache Flink 的内置 SQL 函数。用户不再「先导出数据 → 调 API → 等结果 → 写回业务系统」，而是在流处理 SQL 里直接写 FORECAST(...) 或异常检测函数，模型推理作为流水线的一个算子，在事件流过时同步产出预测值。模型跑在 CPU 上，在 Confluent Cloud 全托管、或本地 Confluent Platform 里就地执行。作者把这种「持续捕获—处理—治理—服务当前业务上下文」的架构命名为 Streamhouse，并明确把时序模型与 LLM、统计模型并列成 Streamhouse 的「stream-native intelligence」层。

## 行业痛点 (Why)
预测的价值随时间衰减：一次生产批次跑完、一次缺货发生、一笔支付授权完成之后才送到的准确预测，等于没用。传统做法是把流数据落进数仓/特征库，再由另一个服务调用模型端点，中间的批量延迟与系统边界让「信号」永远追不上「决策」。而每个业务序列单独训一个模型，人力上不可规模化——一家制造或零售企业可能有上万个序列。

## 旧范式 vs 新范式
- **旧做法**：时序 AI = 「模型即端点」：数据落库 → 特征工程 → 每个序列各训一个模型（或调一个预测 API）→ 结果写回 → 业务系统再读。模型在数据流的旁边，靠批量作业定期对齐，延迟以小时/天计；模型是 GPU 上的独立服务，与数据管道分属两套运维。
- **新做法**：时序 AI = 「模型即算子」：预训练时序基础模型以 SQL 函数形态内嵌进 Flink，预测/异常检测在事件流的同一条管道里完成，结果与产生它的事件并排流向下游应用和 agent。零训练起步（一个预训练模型覆盖多序列），按需微调，纯 CPU 执行，云上全托管或本地就地跑。模型不再是需要对接的外部服务，而是流处理器的一个内置能力。

## 生产力影响 (How)
把「预测上线」从跨团队集成分解为一条 SQL。开发者在已有的 Flink 作业里加一个函数调用即可获得预测能力，无需建特征库、无需模型服务、无需 GPU 预算，也不需要为每个序列维护一套训练流水线。这让「实时预测」第一次具备了与普通流式聚合相同的部署成本，把时序 AI 的适用面从「少数关键指标」扩大到「全量业务序列」。

## 采用成本
已有 Flink/Confluent 栈的组织近乎零增量成本（一个函数调用）；从零开始则需要引入流处理平台，是实质性架构投入。CPU 推理成本低于 GPU 服务，但要接受预训练基础模型在特定领域的精度上限——文中明确建议按任务微调或叠加业务规则。需要理解模型对上下文窗口与最近观测的要求。
