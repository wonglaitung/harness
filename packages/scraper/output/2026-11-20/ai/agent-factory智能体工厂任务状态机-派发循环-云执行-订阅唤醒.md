# Agent Factory（智能体工厂：任务状态机 + 派发循环 + 云执行 + 订阅唤醒）

## 技术定义 (What)
OpenAI 内部构建的 Performance Factory 把「修一个性能回归」这种完整工作流拆成四个可复用组件：任务服务（用 Markdown 配置定义任务状态、允许的状态迁移、哪些步骤必须人来做）、派发循环（周期性检查哪些任务已就绪，为每个就绪任务启动一次 Codex turn）、云端执行 API（在受控文件系统/网络权限下跑命令）、订阅机制（GitHub review 评论、部署完成等外部事件唤回 Agent）。核心不是「让 AI 写代码」，而是「让 Agent 接管一个跨天、跨人、跨部署环节的长流程」，任务本身携带状态与结论，可在 Agent 与人之间来回传递并从中断处恢复。

## 行业痛点 (Why)
Agentic 开发节奏下，传统性能工程不可持续。一个性能回归的完整闭环包含：发现告警 → 定位根因 → 提修复 → 等 code review → 部署 → 验证性能是否回到基线。每一步都要工程师在场，人变成了「告警与 Codex 之间的搬运工」：把告警粘进 Codex，再把结论粘回 Slack。告警堆积后，连「哪个回归需要优先看」都要靠翻 Slack 线程。单次会话型 Agent 无法跨越 code review 和部署这两个动辄数小时到数天的等待窗口。

## 旧范式 vs 新范式
- **旧做法**：三阶段：① Pre-Codex —— 人工看指标、翻日志、比 trace、登机器 debug，读代码定位，依赖对服务的深度知识，积累了 30+ 个性能工具但仍然「该看哪里」靠人猜；② Codex 作为结对伙伴 —— 能搜代码库、找指标 trace、跑 profiling，但工程师必须全程掌舵，决定用哪个工具、下一步查什么；③ 把流程写成 `perf-forensics` skill 后用 eval 精调，做到「给一个告警，一次运行返回诊断」—— 但自动化止于此，后续修复与验证仍回到人手上。
- **新做法**：工作单位从「一次 Agent 会话」升级为「一个有状态的长期任务」。任务服务里用 Markdown 定义状态机与各状态下 Agent 的指令，派发循环按状态分配 Agent，订阅把外部事件（review 评论、部署完成）变成唤醒信号。Agent 跑完一步就记录结论并把任务推进到下一状态；需要人判断的步骤显式标注给人。多个 workflow 之间还能互相开任务：一个负责「发现优化机会」的 workflow 可以给另一个负责「实现并测试」的 workflow 开单。三个月跑了 1,700+ 次调查、根因定位 600+ 例，即每天约 17 次自动调查。

## 生产力影响 (How)
把「长时程、有等待窗口、需要跨角色交接」的工程流程变成可编排资产。关键可迁移点是那个演进路径：人工 → Agent 结对 → 把流程沉淀成 skill 并用历史案例做 eval → 人退化为搬运工（此时该做自动化了）→ 搬到云端自动触发 → 建成工厂。任何有重复性、有告警源、有明确完成判据的运维/工程流程都可照此改造。注意瓶颈从「Agent 能力」转移到「状态机设计」和「谁来定义完成判据」。

## 采用成本
自建成本中高：需要任务服务 + 派发循环 + 云执行沙箱 + 事件订阅四件套，加上把团队隐性流程显式写成状态机与 Prompt 的组织成本。OpenAI 未开源该实现，只能参考架构自研。最大隐性成本在「用历史回归案例构建 eval」——这是把 skill 从不可靠变成可交付的前提。
