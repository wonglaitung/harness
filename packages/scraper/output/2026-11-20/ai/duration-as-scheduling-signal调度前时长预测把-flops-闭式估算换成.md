# Duration-as-Scheduling-Signal（调度前时长预测：把 FLOPs 闭式估算换成仅用提交配置的监督回归）

## 技术定义 (What)
把「一个微调作业要跑多久」当作监督回归问题而不是物理估算问题。输入只允许使用调度发生前就已知的信息（超参数、数据集规模、模型标识、GPU 分配），完全不含运行时日志或部分进度；在此基础上人为派生暴露开销的特征（评测周期内处理的样本数 num_eval_data、checkpoint 保存次数 num_saves 与参数量 num_params_saved、每卡 token 量），并把传统 FLOP 估算（MFU 固定 0.45）作为一个特征喂进去，让模型从「算力项」出发学习修正项。结果：CatBoost 在 24 特征下达到 R²=0.98、MAE 1.71h、中位误差 0.51h，而 FLOP 闭式估算仅 R²=0.31、MAE 12.41h（272 个真实 H200 SFT 作业，7382 GPU-hours）。

## 行业痛点 (Why)
共享 GPU 集群每天都要决定「哪个作业上哪张卡、按什么顺序」。这个计划的好坏完全取决于时长估计。估早了：GPU 空转等下一个作业派发；估晚了：后面排队的全部顺延，实验延期、交付日期漂移。而团队普遍用的是 (6·P·D)/(N·FLOPS·MFU) 这种闭式计算——它只描述优化循环本身，漏掉了环境搭建、模型下载与加载、分词、周期性评测、checkpoint 上传、最终权重写对象存储，以及多租户下的网络与存储 I/O 争用。两个名义算力相同的作业能差出几小时。

## 旧范式 vs 新范式
- **旧做法**：用 FLOPs 闭式公式估算，MFU 靠猜（实际 30–60%，具体作业该取多少事先不知道）；估算结果被认为「大概是这个量级」，调度器按这个数排队，误差被当作不可避免的噪声接受。
- **新做法**：把时长当作可从历史作业学习的目标量：只用调度前可得特征 + 显式派生「开销特征」+ 把 FLOP 估算本身降级为输入特征之一。于是估计从「算力模型」变成「端到端 wall-clock 模型」，能把非算力开销（评测节奏、checkpoint 策略、每卡负载、微调范式 LoRA vs 全参）与它们的非线性交互一起学进去。这等价于承认：作业时长是一个数据可解的问题，而非物理不可解的问题。

## 生产力影响 (How)
直接换算成 GPU 利用率与排队时间。同一批作业，MAE 从 12.41h 降到 1.71h（中位 0.51h），意味着调度器可以在作业派发前就做出准确的装箱决策，显著减少「作业提前几小时跑完而卡空着」与「作业晚了导致整队顺延」两种浪费。方法本身是通用的：任何 GPU 稀缺、按作业排队的组织都能用自己集群的日志复刻，成本仅是一次 CatBoost 训练。

## 采用成本
低-中。方法侧是常规 CatBoost + 特征工程（18 组候选特征、24 个入选），无需特殊基建；主要成本是历史日志采集（需要记录作业配置 + wall-clock + 栈类型）。论文与完整方法即将在 arXiv 发布。
